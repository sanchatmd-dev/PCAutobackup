# PC AutoBackup

แอป Windows สำหรับสำรองไฟล์แบบเข้ารหัสไปยัง **Google Drive**, **External HDD/SSD** หรือ **โฟลเดอร์ที่กำหนดเอง** พร้อมกู้คืนบนเครื่องใหม่ด้วยกุญแจกู้คืน หน้าต่างเป็น WPF native ภาษาไทย ไม่มี Electron หรือ browser runtime ค้างเบื้องหลัง

[หน้าแอป](https://sanchatmd-dev.github.io/PCAutobackup/) · [นโยบายความเป็นส่วนตัว](https://sanchatmd-dev.github.io/PCAutobackup/privacy.html) · [เงื่อนไขการใช้](https://sanchatmd-dev.github.io/PCAutobackup/terms.html)

## ความสามารถ

- เลือก **การตั้งค่า → ภาษาของแอป → English** เพื่อใช้ภาษาอังกฤษ เปลี่ยนแล้วบันทึกทันทีและจำเมื่อเปิดใหม่ ภาษาไทยเป็นค่าเริ่มต้น เปลี่ยนภาษาไม่เปลี่ยนเวลา/โฟลเดอร์/บัญชี/การเก็บประวัติ ข้อความที่มาจาก Windows หรือบริการภายนอกอาจใช้ภาษาของบริการนั้น

- สำรองผ่าน Windows Task Scheduler วันละ 1–24 รอบตามเวลาที่เลือก ค่าเริ่มต้นวันละครั้ง 21:00; Worker เปิดเฉพาะเวลาทำงานแล้วออก เหลือไอคอนเมฆในถาดระบบซึ่งใช้ RAM ต่ำ
- ติดตั้งทางลัด Desktop/Start Menu และเริ่มถาดระบบเมื่อเข้าสู่ Windows กดปิดหรือย่อหน้าต่างแล้วงานที่กำลังทำจะดำเนินต่อจนเสร็จ
- Google Drive เป็นค่าเริ่มต้น ล็อกอินผ่านเบราว์เซอร์ของระบบด้วย OAuth PKCE และยืนยันอีเมลจริงจาก Google แอปไม่รับรหัสผ่าน Google
- อ่านไฟล์ทีละ chunk 4 MiB เข้ารหัส AES-256-GCM และใช้ keyed content IDs เพื่อไม่เก็บ chunk เดิมซ้ำใน repository เดียวกัน
- ค่าเริ่มต้นเก็บประวัติ **7 วัน**; เปลี่ยนจำนวนวันได้; `0` หมายถึงเก็บเฉพาะชุดล่าสุดที่สำเร็จ
- กำหนดเพดานพื้นที่ Backup เป็น GB หรือเว้นว่างเพื่อไม่กำหนดเพดาน ค่าที่นับคือข้อมูลสำรองของ repository นี้ ไม่ใช่พื้นที่ทั้งหมดของบัญชี Google
- เมื่อพื้นที่ไม่พอ ล้างประวัติเก่าสุดก่อน จึงอาจเก็บย้อนหลังสั้นกว่าจำนวนวันที่ตั้งไว้ หากชุดใหม่เพียงชุดเดียวเกินเพดาน จะไม่ยืนยันชุดใหม่และรักษาชุดล่าสุดที่สำเร็จไว้
- ไฟล์ที่ลบในต้นทางจะหายจากชุดล่าสุดเมื่อสำรองรอบใหม่สำเร็จ แต่ยังอยู่ในประวัติที่ไม่ถูกล้าง
- เลือกหลายโฟลเดอร์ แสดงความคืบหน้า ยกเลิกงาน และกู้คืนไปยังโฟลเดอร์ว่างโดยไม่เขียนทับไฟล์เดิม
- ดิสก์ภายนอกใช้ volume identity เพื่อไม่เผลอเขียนลงดิสก์อื่นเมื่ออักษรไดรฟ์เปลี่ยน
- แนบรายชื่อโปรแกรมที่ติดตั้งจาก Windows Registry เป็น JSON ได้ เพื่อช่วยติดตั้งใหม่ด้วยตัวเอง

## เริ่มใช้งาน

**สำหรับผู้ติดตั้งใหม่:** [คู่มือติดตั้งและตั้งค่าสำรองทุกวัน 21:00](docs/installation-guide-th.md) หรือ [ฉบับ HTML สำหรับส่งต่อและพิมพ์](docs/installation-guide-th.html) ครอบคลุมดาวน์โหลด `.exe`, Google OAuth/Drive, โฟลเดอร์ต้นทาง และการเก็บกุญแจกู้คืน

**ติดตั้งจากไฟล์เดียว:** ส่ง `PCAutobackup-win-x64.exe` ให้ผู้รับ ดับเบิลคลิกแล้วตัวติดตั้งจะติดตั้งให้บัญชี Windows ปัจจุบัน สร้างไอคอน Desktop/Start Menu และเปิดแอปเมื่อเสร็จ ไม่ต้องแตก ZIP หรือติดตั้ง .NET เพิ่ม ไม่ต้องใช้สิทธิ์ Administrator หากมีงานสำรองหรือหน้าตั้งค่าเปิดอยู่ ให้ปิดหน้าตั้งค่าและรอให้งานเสร็จก่อนติดตั้ง รุ่นนี้ยังไม่ได้ลงลายเซ็น code signing จึงอาจแสดงชื่อผู้เผยแพร่ที่ไม่รู้จักใน Windows

ตัวติดตั้งไม่รวมบัญชี Google, OAuth client, กุญแจ หรือไฟล์สำรองของผู้พัฒนา ผู้รับเลือกต้นทาง/ปลายทางและตั้ง Google OAuth ของตนเองตามคู่มือด้านล่าง ตัวเลือก ZIP/Install.cmd ยังใช้ได้ตามขั้นตอนต่อไปนี้

1. สร้างหรือดาวน์โหลดชุด Windows จาก workflow แตก ZIP แล้วเปิด `Install.cmd` ไม่ต้องใช้สิทธิ์ผู้ดูแล ตัวติดตั้งคัดลอกไป `%LOCALAPPDATA%\Programs\PCAutobackup` สร้างทางลัด Desktop/Start Menu และเริ่มถาดระบบเมื่อเข้าสู่ Windows หากอัปเดตให้ปิดหน้าตั้งค่าและรอให้งานสำรองเสร็จก่อน ตัวติดตั้งรักษาการตั้งค่า/กุญแจเดิมและปรับพาธ Worker ของ task ที่เปิดไว้ การอัปเดตไม่เปิด **เริ่มพร้อม Windows** กลับมาหากปิดไว้ก่อนอัปเดต เปิดได้จากเมนูถาดระบบ
2. เปิดไอคอน **PC AutoBackup** รูปเมฆบน Desktop เพื่อปรับค่า หรือคลิกไอคอนเมฆในถาดระบบ (อาจอยู่ในเมนูลูกศรซ่อนไอคอน) ชุดแอปรวม .NET runtime มาแล้ว ไม่ต้องติดตั้ง .NET เพิ่ม
3. ใน **โฟลเดอร์ต้นทาง** เพิ่มเฉพาะโฟลเดอร์ที่ต้องการ เช่น Documents, Desktop, Pictures และโฟลเดอร์งาน
4. ใน **พื้นที่จัดเก็บ** เลือก Google Drive และเชื่อมบัญชี หรือเลือกโฟลเดอร์เฉพาะบน External HDD/SSD/ดิสก์อื่น
5. ใน **การตั้งค่า** ส่งออกกุญแจกู้คืนไปยังที่ปลอดภัยนอกคอมเครื่องนี้ เช่น USB อีกตัว ห้ามเก็บสำเนาเพียงชุดเดียวไว้ใน PC ที่กำลังสำรอง
6. ตั้งจำนวนวัน/เพดานพื้นที่ และลอง **สำรองตอนนี้** หนึ่งครั้ง ตรวจรายการประวัติและทดลองกู้คืนไฟล์ก่อนพึ่งพางานอัตโนมัติ
7. เปิดตัวเลือกสำรองอัตโนมัติ กรอก **เวลาสำรองแต่ละวัน** เช่น `21:00` หรือ `09:00, 13:00, 21:00` แล้วบันทึก จากนั้นปิดหน้าต่างได้ ใส่เวลาแบบ 24 ชั่วโมง ไม่ซ้ำกัน สูงสุด 24 รอบต่อวัน

การติดตั้งใหม่ยังไม่เปิดสำรองจนกว่าจะตั้งต้นทาง ปลายทาง กุญแจ และเปิด schedule เอง สำหรับเครื่องที่เปิดสำรองอัตโนมัติไว้แล้ว การเปิดแอป/ถาดระบบจะตรวจรอบที่พลาดและงานสำรองที่ถูกขัดจังหวะ แล้วเรียก Worker ตามความจำเป็น

หาก Worker รอบอัตโนมัติพบว่างานอื่นกำลังใช้การตั้งค่าเดียวกัน จะจบด้วย exit code `0` และบันทึก **ข้ามเพราะมีงานกำลังทำอยู่** แยกไว้ใน `configuration.json.scheduled-skip.json` หน้า **ภาพรวม** แสดงรอบที่ข้ามล่าสุดพร้อมเวลา โดยไม่ทับสถานะงานที่กำลังอัปโหลดหรือชุดสำเร็จล่าสุด และไม่เริ่มอัปโหลดซ้ำ การข้ามไม่ถือว่าสำรองสำเร็จ; รอบถัดไปยังตรวจงานที่ถึงกำหนดตามปกติ ข้อผิดพลาดจริงยังคืน exit code `1` ส่วน Task Scheduler ตั้ง `IgnoreNew` จึงอาจกันการเปิด Worker ซ้ำของ task เดียวกันก่อนถึงตัวแอปได้

หาก Google upload session ของก้อนข้อมูลปัจจุบันตอบ HTTP 404/410 ตัว Worker จะตรวจว่าก้อนนั้นบันทึกแล้วหรือไม่ และเริ่ม session ใหม่ได้สูงสุดสองครั้งโดยไม่เริ่มสำรองทั้งโฟลเดอร์ใหม่ กรณีคำตอบหลังอัปโหลดหายจะตรวจ SHA-256 ของวัตถุที่เป็นของ upload เดิมก่อนถือว่าสำเร็จ หากยังผิดพลาด งานจะล้มเหลวและเก็บชุดสำเร็จก่อนหน้าไว้ ข้อนี้ไม่ใช่การรับประกันว่างานที่ถูกปิดโปรเซสจะต่อจาก byte เดิมได้เสมอ

## ตั้งค่า Google Drive ครั้งแรก

แอปไม่มี OAuth client ของผู้พัฒนาฝังมาให้ ผู้ติดตั้งต้องใช้ Google Cloud project ของตนเอง:

1. เข้า [Google Cloud Console](https://console.cloud.google.com/) สร้างหรือเลือก project และเปิด **Google Drive API**
2. ตั้งค่า OAuth consent screen / Google Auth Platform ใส่ข้อมูลแอป หากใช้สถานะ Testing ให้เพิ่มบัญชีที่จะใช้ในรายชื่อ test users
3. สร้าง OAuth Client ID ชนิด **Desktop app** แล้วดาวน์โหลด client JSON
4. ที่หน้าพื้นที่จัดเก็บของ PC AutoBackup กดนำเข้า OAuth client JSON (หรือระบุ Client ID/Client secret ของ Desktop client)
5. กด **เชื่อมต่อ Google** เลือกบัญชี/เข้าสู่ระบบบนหน้า Google และอนุญาตสิทธิ์ Drive จากนั้นแอปจะแสดงอีเมลที่ Google ยืนยันจริง อีเมลที่พิมพ์ในแอปเป็นเพียงตัวช่วยเลือกบัญชี

ดูขั้นตอนหน้าจอปัจจุบัน การทดสอบไฟล์จำลอง และการแก้ปัญหาที่ [คู่มือ Google Desktop OAuth](docs/google-setup.md)

สิทธิ์ที่ใช้: `openid`, `email`, `https://www.googleapis.com/auth/drive.file` สำหรับไฟล์ที่แอปสร้าง/ได้รับอนุญาต โฟลเดอร์ที่แอปสร้างคือ `PC AutoBackup` และแยก repository ตามเครื่อง ไม่แก้ไฟล์ทั่วไปนอกคลังของแอป

**เมื่อต้องกู้คืนบนคอมใหม่ ใช้ Google account เดิมและ OAuth application/project เดิม** จึงจะค้นพบ repository เดิมภายใต้ `drive.file` ได้ รุ่นนี้ยังไม่มี Google Picker เพื่อรับสิทธิ์ข้าม OAuth application จึงควรเก็บ client JSON ไว้ด้วย (แยกจากกุญแจกู้คืนตามสมควร)

หากโฟลเดอร์คลังของเครื่องนี้ถูกย้ายไปถังขยะของ Google Drive แอปจะหยุดก่อนอ่านหรือเขียน และแจ้งให้กู้คืนโฟลเดอร์จากถังขยะก่อน ไม่ถือว่าเป็นคลังว่าง การดาวน์โหลดจาก Drive ที่ไม่มีข้อมูลเข้ามาเกิน 3 นาทีจะล้มเหลวแทนการค้าง หน้าล็อกอินรอ callback ต่อเมื่อมีการเชื่อมต่อที่ไม่ใช่ callback เข้ามาที่พอร์ตชั่วคราว จนครบเวลา 5 นาที

Google OAuth project ที่อยู่ในสถานะ External/Testing อาจมี refresh token อายุ 7 วันสำหรับสิทธิ์ Drive ทำให้ต้องเชื่อมใหม่ ควรตั้งสถานะและปฏิบัติตามข้อกำหนดของ Google ให้เหมาะกับงานสำรองอัตโนมัติระยะยาว

เอกสารทางการ: [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [Token expiration](https://developers.google.com/identity/protocols/oauth2), [Resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads)

## กู้คืนเมื่อเปลี่ยนเครื่อง

1. ติดตั้ง/เปิดแอปบนเครื่องใหม่ แล้วนำเข้าไฟล์กุญแจ `.pcakey` ที่ส่งออกไว้
2. เปิด **ประวัติและกู้คืน** เลือกคลังสำรองจากโฟลเดอร์บนดิสก์ หรือเชื่อม Google ด้วย OAuth application เดิมแล้วเลือกเครื่องต้นทางจากรายการ
3. เลือกจุดกู้คืน และเลือก **โฟลเดอร์ว่าง** เป็นปลายทาง
4. แอปตรวจความถูกต้องและถอดรหัสไฟล์ แล้วสร้างโฟลเดอร์ต้นทางแยกตามชื่อที่อ่านออกและรหัสคงที่ ย้าย Documents/Desktop/โฟลเดอร์งานไปที่ที่เหมาะสมในเครื่องใหม่หลังตรวจสอบผล
5. หากจะเริ่มสำรองเครื่องใหม่ ให้เลือก repository ใหม่สำหรับเครื่องใหม่ คลังเดิมมีเจ้าของเครื่องกำกับไว้เพื่อป้องกันคอมใหม่ที่ว่างทำให้ประวัติเครื่องเดิมถูกล้าง

**เมื่อข้อมูลในคลังเสียบางส่วน:** ชุดสำรองที่ manifest อ่านไม่ได้ยังแสดงในรายการ โดยชื่อเครื่องเป็น `Damaged snapshot (unreadable) / ชุดสำรองเสียหาย อ่านไม่ได้` และไม่นับในจำนวนชุดที่กู้คืนได้ ชุดอื่นยังเลือกกู้คืนได้ตามปกติ ระหว่างกู้คืน ไฟล์ที่ chunk หายหรือตรวจความถูกต้องไม่ผ่านจะถูกข้ามเฉพาะไฟล์นั้น ไม่มีไฟล์บางส่วนค้างไว้ ไฟล์อื่นกู้ต่อจนครบ หน้าจอแสดง **กู้คืนได้บางส่วน** พร้อมจำนวนไฟล์ที่กู้ไม่ได้ และบันทึกรายการทั้งหมดไว้ใน `PCAutobackup-unrestored-files.txt` ในโฟลเดอร์ปลายทาง หากกู้ไม่ได้เลยสักไฟล์ งานจะล้มเหลวพร้อมสาเหตุ ข้อผิดพลาดของเครือข่าย ดิสก์ปลายทาง หรือการยกเลิกยังหยุดงานทั้งชุดเช่นเดิม กู้คืนจากคลังบนสื่ออ่านอย่างเดียวหรือแชร์แบบอ่านอย่างเดียวได้ รอบสำรองใหม่ยังหยุดเมื่อพบ manifest ที่อ่านไม่ได้ โดยข้อความระบุรหัสชุดสำรองนั้น รุ่นนี้ยังไม่มีคำสั่งลบหรือกักชุดที่เสียจากในแอป

ไฟล์ `.pcakey` คือกุญแจ 256 บิต ผู้ที่มีทั้งกุญแจและคลังสามารถอ่านข้อมูลได้ หากกุญแจหายและไม่สามารถเปิดข้อมูล DPAPI ในบัญชี Windows เดิมได้ แอปไม่มีระบบรีเซ็ตเพื่อถอดรหัสข้อมูลเดิม

ถ้าเครื่องนี้มีกุญแจสำรองใช้งานอยู่แล้ว การนำเข้ากุญแจอีกคลังจะใช้สำหรับการกู้คืนใน session นี้เท่านั้น ไม่แทนที่กุญแจของงานอัตโนมัติเดิม เมื่อเปิดแอปใหม่ต้องนำเข้ากุญแจกู้คืนต่างคลังอีกครั้ง สำหรับการติดตั้งใหม่ที่ยังไม่มีกุญแจ แอปจะบันทึกกุญแจแรกด้วย DPAPI

## RAM และการทำงานเบื้องหลัง

**การส่งข้อมูลพร้อมกัน:** รุ่นใช้งานจริงกำหนดสำรองสูงสุด 16 chunks และกู้คืนสูงสุด 16 chunks พร้อมกัน โดยใช้ buffer และคิวจำกัด Google Drive ส่ง encrypted chunk ขนาดไม่เกิน 4 MiB + 32 bytes ใน data request เดียว ค่า 32 ยังใช้เฉพาะการทดลอง การกู้คืนเขียนไฟล์ตามลำดับเดิมและตรวจความถูกต้องก่อนใช้งาน RAM สูงขึ้นขณะทำงาน และถูกคืนเมื่อโปรเซสงานปิด ผลวัดและข้อจำกัดอยู่ใน `docs/validation.md`

**ถ้างานสำรองยังไม่เสร็จเมื่อถึงรอบใหม่:** งานเดิมทำต่อจนเสร็จ Task Scheduler ใช้ `IgnoreNew` จึงไม่เปิด Worker ซ้อนและไม่ต่อคิวให้เริ่มทันทีหลังจบงาน ระบบจะตรวจรอบที่พลาดเมื่อมี trigger ถัดไป เช่น รอบเวลาถัดไป เปิดแอป เข้าสู่ Windows ปลดล็อก หรือกลับจาก Sleep โดยรวมรอบที่พลาดเป็นการสำรองข้อมูลปัจจุบันหนึ่งรอบ การอัปโหลดไฟล์ใหญ่แบ่งเป็น chunks 4 MiB; ถ้างานหยุดกลางคัน รอบใหม่ใช้ chunks ที่อัปโหลดสำเร็จแล้วซ้ำได้ แต่ต้องอ่าน/hash ต้นทางอีกครั้ง และไม่ใช่การ resume ตรง byte ของไฟล์

เมื่อปิดหรือย่อหน้าต่างที่ไม่มีงานค้าง WPF จะออก เหลือ `PCAutobackup.Tray.exe` ซึ่งใช้ Win32 message loop ไม่มี polling และไม่มี WPF/Chromium ในถาดระบบ ผลวัด Windows 11 x64 ขณะพักประมาณ **35–38 MiB working set / 8–10 MiB private memory** ไม่ใช่เพดานรับประกัน หากปิดหน้าต่างระหว่างสำรองหรือกู้คืน หน้าต่างจะซ่อนและทำงานจนเสร็จแล้วออก เปิดจาก Desktop/ถาดระบบระหว่างนั้นจะเรียกหน้าต่างเดิมกลับมา หากงานที่ซ่อนอยู่ล้มเหลว หรือกู้คืนได้เพียงบางส่วน หน้าต่างจะกลับมาแสดงผลนั้นและรอให้ผู้ใช้ปิดเอง ไม่ออกเงียบ ๆ

คลิกขวาไอคอนถาดระบบเพื่อเปิดหน้าตั้งค่า สำรองตอนนี้ เปิด/ปิด **เริ่มพร้อม Windows** หรือออกจากถาดระบบ การออกจากถาดระบบไม่ปิดตารางสำรอง หากต้องการหยุดสำรองอัตโนมัติให้ปิดในหน้าการตั้งค่าด้วย Startup เป็นของผู้ใช้ Windows ปัจจุบันและเริ่มหลังเข้าสู่ระบบ ไม่ทำงานก่อนล็อกอิน ดู [Windows Run registry keys](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)

หากถูกบังคับปิดจาก Task Manager แอปไม่เปิดตัวเองซ้ำทันที เมื่อเปิดแอปอีกครั้งหรือเข้าสู่ Windows ครั้งถัดไป จะกลับมาทำงานได้โดยไม่ติด lock เก่า งานสำรองที่หยุดกลางคันจะเริ่มใหม่เมื่อเปิด schedule ไว้ ใช้ chunks ที่สำเร็จแล้วซ้ำ และรักษาชุดสำเร็จก่อนหน้า ไม่ใช่การ resume ตรง byte ของไฟล์ ส่วนงานกู้คืนที่ถูกบังคับปิดต้องเริ่มใหม่ไปยังโฟลเดอร์ว่าง

ระหว่างสำรองอ่านเนื้อหาเป็น chunk และอัปโหลดทีละส่วน แต่ข้อมูลรายการไฟล์และชุด chunk references ยังใช้ RAM ตามจำนวนไฟล์/ประวัติ จึงไม่รับประกันเพดาน 50 MB ระหว่างทำงาน ไม่โหลดเนื้อหาไฟล์ขนาดใหญ่ทั้งไฟล์เข้าหน่วยความจำ ประวัติแต่ละ manifest ถูกอ่านทีละชุด ขนาด encrypted manifest จำกัด 256 MiB

การทดสอบ Windows 11 x64 ด้วยไฟล์สุ่ม 128 MiB + ไฟล์ภาษาไทยหนึ่งไฟล์ วัด peak working set ของ worker ได้ประมาณ **75.5 MiB รอบแรก** และ **44.6 MiB รอบไม่เปลี่ยนข้อมูล** ตัวเลขนี้เป็นผลจากชุดทดสอบเล็ก ไม่ใช่เพดานสำหรับทุก workload รายละเอียดอยู่ใน [ผลตรวจสอบ](docs/validation.md)

งานประจำวันสแกนและ hash ไฟล์ที่เลือกทั้งหมด เพื่อจับการเปลี่ยนแปลง แต่ไม่ดาวน์โหลด chunk ที่สำรองไว้แล้วทุกวัน ข้อมูลเดิมจะถูกตรวจสอบการถอดรหัสและความถูกต้องเมื่อกู้คืน การตรวจ corruption ทุกวันแบบ full scrub ยังไม่รองรับ

ตารางเวลาใช้บัญชี Windows ปัจจุบันแบบ **ผู้ใช้ต้องล็อกอินอยู่** ไม่เก็บรหัสผ่าน Windows หากปิดเครื่องหรือ Sleep ตอนถึงรอบ เมื่อเข้าสู่ Windows ปลดล็อก หรือ Windows แจ้งกลับจาก Sleep จะเรียกตรวจงานตกค้างหลังประมาณ 1 นาที พร้อมเปิด StartWhenAvailable ของ Task Scheduler ไว้ด้วย ไม่ปลุกเครื่องเองและไม่ทำงานก่อนเข้าสู่บัญชี Windows เดิม หากพลาดหลายรอบจะสำรองข้อมูลปัจจุบันชดเชยครั้งเดียว ไม่สร้างภาพย้อนหลังที่ไม่มีจริง และไม่สำรองซ้ำหากมีงานสำเร็จที่เริ่มตั้งแต่รอบล่าสุดแล้ว

งานล้มเหลวให้ Task Scheduler ลองใหม่ทุก 5 นาที สูงสุด 3 ครั้งต่อ trigger เช่น รอเครือข่ายหลังกลับจาก Sleep งานไม่รันซ้อนกัน หากรอบใหม่มาถึงขณะงานเดิมยังทำอยู่จะไม่เริ่มอีก process ให้ตรวจผลในแอป งานที่ค้าง/ชิ้นส่วนที่อัปโหลดสำเร็จถูกใช้ซ้ำเมื่อรอบใหม่เริ่มได้ ไม่รับประกัน resume ตรง byte ของไฟล์ที่อ่านค้างเมื่อปิดเครื่อง การเริ่มจริงขึ้นกับ Windows, สถานะล็อกอิน และความพร้อมของต้นทาง/ปลายทาง

การตั้งค่าเก่าที่มีเวลาเดียวจะรักษาเวลานั้นไว้ เมื่อแก้เวลาผ่านหน้าตั้งค่า ระบบจะบันทึกรายการหลายเวลาให้ใหม่ ตัวเลือกหลายโฟลเดอร์มีอยู่ที่ **โฟลเดอร์ต้นทาง → เพิ่มโฟลเดอร์** เลือกหลายโฟลเดอร์ใน dialog หรือเพิ่มทีละโฟลเดอร์ได้

ปุ่ม **นำออก / Remove** นำโฟลเดอร์ออกจากรายการสำรองทันที แต่ไม่ลบไฟล์ต้นฉบับ หลังนำออกจะมี **เลิกทำ / Undo** และ **ยืนยันนำออก / Confirm removal** คู่กัน เลิกทำคืนรายการพร้อมรหัส ชื่อ และลำดับเดิม ส่วนยืนยันนำออกลบประวัติของรายการนั้น ทำให้คืนผ่านประวัติไม่ได้ แถบนี้ซ่อนเมื่อครบ 1 นาที แต่รายการที่ยังไม่ยืนยันยังเก็บอยู่ในไฟล์การตั้งค่าข้ามการปิดแอปและรีเฟรช ไม่มีการล้างรายการเก่าอัตโนมัติเมื่อเกิน 20 รายการ

ปุ่ม **คืนโฟลเดอร์ / Restore folders** คืนทุกรายการที่ยังไม่ได้ยืนยันนำออก หากมี ID หรือพาธซ้ำจะเก็บรายการที่คืนไม่ได้ไว้ในประวัติ ปุ่ม **ล้างประวัติ / Clear history** ถามยืนยันก่อนล้างประวัติทั้งหมด โดยไม่คืนโฟลเดอร์และไม่ลบไฟล์ต้นฉบับ ประวัตินี้คืนเฉพาะรายการโฟลเดอร์ ไม่คืนเวอร์ชันสำรองที่ retention ล้างแล้ว

อ้างอิง Windows: [StartWhenAvailable](https://learn.microsoft.com/en-us/windows/win32/taskschd/tasksettings-startwhenavailable), [session-state triggers](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-sessionstatechangetrigger-triggergroup-element), [event triggers](https://learn.microsoft.com/en-us/windows/win32/taskschd/taskschedulerschema-eventtrigger-triggergroup-element)

## ข้อจำกัดที่ควรเข้าใจก่อนใช้

- เป็น **file backup** ไม่ใช่ disk image หรือ bare-metal restore ไม่คัดลอก Windows/ไดรเวอร์ ไม่รับประกันย้ายโปรแกรมและการตั้งค่าข้าม OS ทุกเวอร์ชัน รายชื่อโปรแกรมเป็นข้อมูลช่วยติดตั้งเอง ไม่ได้มีตัวติดตั้งหรือ license มาด้วย
- ไม่ย้าย cookie/session/password ของ browser หรือไฟล์ credential ที่ผูกกับเครื่องให้ใช้งานข้ามเครื่องอัตโนมัติ ใช้ระบบ sync/export ของโปรแกรมนั้นเมื่อจำเป็น
- ไม่มี VSS หรือ application-aware database snapshot: ปิดโปรแกรมที่เขียนไฟล์ฐานข้อมูล/VM/อีเมลก่อนสำรอง ถ้าเปิดอ่านไม่ได้หรือไฟล์เปลี่ยนระหว่างอ่าน งานจะล้มเหลวและไม่ยืนยัน snapshot ใหม่
- ระหว่างสำรองจะข้าม junction/symlink ภายในต้นทาง พร้อมแจ้งเส้นทางที่ข้าม ไม่หยุดทั้งรอบและไม่เดินวนตามลิงก์ หากปลายทางอยู่ในต้นทางที่เลือก จะสำรองผ่านเส้นทางจริงเพียงครั้งเดียว เช่น `Project/root-matbot-w1/data` ชี้ไป `Project/MATBot/data` ให้เลือก `Project` แล้วข้อมูลจะอยู่ที่ `MATBot/data` ในชุดสำรอง
- ลิงก์ที่ชี้ออกนอกต้นทาง ปลายทางหาย หรือผ่านลิงก์อื่น จะถูกข้ามพร้อมคำเตือนว่าไม่รวมปลายทางนั้น และงดล้างชุดสำรองเก่าตามอายุ/โควตาในรอบนั้น เพื่อไม่สูญเสียประวัติ หากต้องการข้อมูลนอกต้นทาง ให้เพิ่มโฟลเดอร์จริงนั้นเป็นต้นทางด้วย การกู้คืนไม่สร้าง junction/symlink กลับให้อัตโนมัติ
- ต้นทางที่เลือกโดยตรงและเส้นทางแม่ต้องไม่เป็น reparse point; cloud placeholder หรือ reparse point ชนิดอื่นยังหยุดงานเพื่อไม่ตีความข้อมูลที่อ่านไม่ได้ว่าเป็นการลบ เลือกไฟล์ local ที่ดาวน์โหลดครบแล้ว การกู้คืนยังไม่อนุญาตให้เขียนผ่าน reparse point
- ไม่รักษา ACL, alternate data streams, EFS certificates หรือ Windows account identity; กู้เนื้อหาไฟล์ โครงสร้างโฟลเดอร์ และเวลาแก้ไขไฟล์ที่รองรับ
- ชื่อไฟล์หรือโฟลเดอร์ในต้นทางที่กู้คืนบน Windows ไม่ได้จะหยุดรอบนั้นก่อนยืนยัน snapshot พร้อมระบุพาธ: ชื่อที่ลงท้ายด้วยจุดหรือช่องว่าง ชื่ออุปกรณ์ที่สงวนไว้ (เช่น `CON`, `AUX`) ชื่อที่มี UTF-16 surrogate ไม่ครบคู่ และชื่อสองชื่อในโฟลเดอร์เดียวกันที่ต่างกันเฉพาะตัวพิมพ์เล็ก/ใหญ่ (พบได้ในโฟลเดอร์แบบ case-sensitive ของ WSL) ให้เปลี่ยนชื่อแล้วสำรองใหม่ รุ่นก่อนหน้าอาจยืนยัน snapshot ที่อ่านกลับไม่ได้ในกรณีเหล่านี้
- คลังเก็บ chunk ทั้งหมดในโฟลเดอร์เดียว และไฟล์เล็กหนึ่งไฟล์ใช้หนึ่ง chunk Google Drive จำกัด 500,000 รายการต่อโฟลเดอร์ ([Drive FAQ for admins](https://support.google.com/a/answer/2490100)) ต้นทางที่มีไฟล์ไม่ซ้ำกันใกล้จำนวนนี้ รวมเวอร์ชันเก่าที่ยังไม่ถูกล้าง จะอัปโหลดต่อไม่ได้เมื่อถึงเพดาน ดิสก์ FAT32 รับได้ราว 9,000 chunk ต่อโฟลเดอร์ ควรใช้ NTFS หรือ exFAT รุ่นนี้ยังไม่แบ่ง chunk เป็นโฟลเดอร์ย่อย
- เมื่อถึง retention/quota แอปจะลบเฉพาะ manifest/chunk ของคลังที่ไม่มี snapshot ที่เหลืออ้างถึง และคงชุดล่าสุดไว้ การลดวัน/โควตาอาจทำให้กู้เวอร์ชันเก่าไม่ได้ การล้างจะหยุดโดยไม่ลบอะไรเมื่อพบ snapshot ที่ไม่อยู่ในรายการตอนเริ่มรอบ หรือเมื่อ snapshot ที่ต้องเก็บไว้อ้างถึง chunk ที่หาย ส่วน snapshot ที่หมดอายุแล้วจะถูกล้างตามปกติแม้ขาด chunk หาก chunk ใดลบไม่ได้ การล้างจะทำรายการอื่นต่อและรายงานจำนวนที่ค้าง
- เพดานพื้นที่เป็นนโยบายข้อมูลที่ commit แล้ว ระหว่าง staging snapshot ใหม่ต้องมีพื้นที่เผื่อสำหรับชุดเก่าและส่วนที่เปลี่ยน และอาจมี orphan ชั่วคราวหากงานหรือ cleanup ถูกขัดจังหวะ แอปจะเก็บกวาดในรอบที่สำเร็จภายหลัง ไม่ใช่ hard filesystem quota
- ใช้หนึ่งเครื่อง/ผู้เขียนต่อ repository ไม่คัดลอก config พร้อม DeviceId ไปใช้เขียนคลังเดียวกันจากหลายเครื่อง Google Drive ไม่มี atomic unique-name/distributed lock; แอปตรวจชื่อซ้ำและหยุดแทนการเลือกไฟล์สุ่ม
- ชุดโปรแกรมนี้ยังไม่ได้เซ็น code-signing certificate และเป็นรุ่นแรก ควรทดลองกู้คืนกับข้อมูลสำคัญที่มีสำเนาอื่นอยู่ก่อน

## Build และทดสอบสำหรับนักพัฒนา

การสำรองไฟล์เล็กใช้คิว chunk ร่วมข้ามไฟล์ โดย production จำกัดงานพร้อมกัน 16 งานและรอทุก upload สำเร็จก่อน commit manifest; หาก upload ล้มเหลวหรือยกเลิก จะไม่ commit ชุดใหม่ ช่วงประมาณขนาดตรวจ ancestor chain ระดับ directory และตรวจ reparse ของแต่ละ entry เพื่อลดการเรียกระบบซ้ำ ส่วนช่วงอ่านเนื้อหายังตรวจเส้นทางเต็มก่อนอ่านแต่ละไฟล์ จึงไม่ได้ตัดการตรวจความปลอดภัยในขั้นอ่านจริง การตรวจ parent แบบเต็มในขั้นอ่านยังมีต้นทุน และยังไม่ได้รวมไฟล์เล็กหลายไฟล์ลงใน chunk เดียว

ต้องใช้ Windows และ [.NET 10 SDK](https://dotnet.microsoft.com/download/dotnet/10.0)

```powershell

dotnet test tests/PCAutobackup.Tests/PCAutobackup.Tests.csproj -c Release
```

## Resume หลังงานสะดุด

เมื่อเน็ตขาด ยกเลิกงาน หรือ process ถูกปิด ระบบเก็บ encrypted chunks ที่บันทึกสำเร็จแล้วในคลัง รอบใหม่อ่านและ hash ต้นทางอีกครั้ง แล้วดาวน์โหลด chunk ที่ยังไม่มี snapshot อ้างถึงมาตรวจการถอดรหัสและเทียบเนื้อหาก่อนใช้ซ้ำ ไม่อัปโหลด chunk ที่ตรวจผ่านอีกครั้ง ก้อนที่ยังไม่ครบหรือเสียหายจะส่งใหม่ทั้งก้อน สูงสุด 4 MiB ไม่บันทึกตำแหน่ง byte ของ Google upload session ข้าม process และไม่ต้องเปิดตัวเลือกเพิ่ม

หลังเครื่องกลับมาใช้งาน ให้เปิดแอป หรือรอ trigger ของตารางที่เปิดไว้ งาน Failed/Interrupted จะถูกพิจารณาให้ลองใหม่ ส่วนการกดยกเลิกโดยตั้งใจไม่บังคับเริ่มใหม่ทันที: การยกเลิกหลังเวลารอบล่าสุดถือว่าผู้ใช้ไม่ต้องการรอบนั้น รวมถึงรอบที่เคยล้มเหลวและรอลองใหม่ รอบเวลาถัดไปยังทำงานตามปกติ สามารถกดสำรองตอนนี้เพื่อใช้ chunks เดิมต่อได้ การปิดหน้าต่างตามปกติระหว่างสำรองยังให้งานทำต่อเบื้องหลัง

ชุดสำรองสำเร็จก่อนหน้ายังกู้คืนได้ งานไม่ครบไม่ปรากฏเป็น snapshot ชิ้นส่วนที่ค้างและไม่ได้ใช้อีกจะถูกล้างหลังเผยแพร่ snapshot ใหม่สำเร็จเท่านั้น หากงานล้มเหลวซ้ำหรือ quota ไม่พอ พื้นที่ชิ้นส่วนค้างจะยังถูกเก็บเพื่อ Resume และอาจเกิน quota ชั่วคราว ต้องเพิ่มพื้นที่หรือปรับข้อมูล/โควตาให้สำรองสำเร็จ ข้อจำกัดนี้ช่วยไม่ให้สูญเสียความคืบหน้า

RAM ใช้ buffer ทีละ chunk ไม่โหลดไฟล์ทั้งไฟล์ แต่ metadata โตตามจำนวนไฟล์และ chunks; ไม่รับประกัน RAM คงที่สำหรับข้อมูลทุกขนาด การทดสอบ process kill ไม่เท่ากับทดสอบไฟดับจริงหรือความทนทานของฮาร์ดแวร์

ผลทดลองเพิ่มเติม: [เปรียบเทียบ 2 กับ 4 ก้อนสำหรับสำรองและกู้คืน](docs/four-chunk-performance-2026-11-08.md) เป็น opt-in เฉพาะการทดสอบ ยังไม่เปิดในรุ่น production; 4 ก้อนเร็วขึ้นในชุดทดสอบแต่มี RAM peak สูงกว่า โดยเฉพาะการกู้คืน

ผลทดลองเพิ่มเติม: [เปรียบเทียบ 4 กับ 8 ก้อน](docs/eight-chunk-performance-2026-11-08.md) แยกทดสอบสำรองและกู้คืน เปิด8เฉพาะharness รุ่นproductionยังไม่เปลี่ยน 8ก้อนเร็วขึ้นในชุดทดสอบแต่มีRAMpeakสูงกว่า4ก้อน.

ผลทดลองเพิ่มเติม: [เปรียบเทียบ 8 กับ 16 ก้อน](docs/sixteen-chunk-performance-2026-11-08.md) แยกสำรองและกู้คืนบนข้อมูลจำลอง 268.47 MB โดย 16 ก้อนลดเวลาสำรอง 28.76% และกู้คืน 32.46% แต่ RAM สูงสุดที่สุ่มวัดเพิ่มเป็น 366.78/325.19 MB ตามลำดับ ใช้เฉพาะ harness ยังไม่เปลี่ยน production หรือตาราง 21:00

ผลทดลองล่าสุด: [เปรียบเทียบ 16 กับ 32 ก้อน](docs/thirtytwo-chunk-performance-2026-11-08.md) แยกสำรองและกู้คืนบนข้อมูลจำลอง 268.47 MB โดย 32 ลดเวลาสำรอง 6.21% และกู้คืน 14.01% แต่ RAM สำรองสูงสุดที่สุ่มวัดเพิ่มจาก 346.32 เป็น 449.25 MB ใช้เฉพาะ harness ยังไม่เปลี่ยน production หรือตาราง 21:00 และยังไม่สรุปผลระดับ TB

ขณะสำรองหรือกู้คืน แอปแสดงเปอร์เซ็นต์ ความเร็วประมวลผล MB/s และเวลาคงเหลือโดยประมาณ ความเร็วคำนวณจาก logical bytes ที่เสร็จต่อเวลาทั้งงาน รวมการสำรวจไฟล์ ไม่ใช่ความเร็วเครือข่ายโดยตรง ช่วงสำรวจยังไม่รู้ขนาดรวมแสดง --% และเมื่อข้อมูลครบจะรอให้ยืนยันงานสำเร็จก่อนแสดง 100% การอัปเดต UI จำกัด 8 ครั้งต่อวินาทีและคิวค้างไม่เกินหนึ่งรายการ ไม่มี timer ที่ทำงานตลอดช่วงพัก

หลังสำรองหรือกู้คืนเสร็จขณะเปิดหน้าตั้งค่าค้างไว้ แอปปล่อยการอ้างอิง chunk buffers และเรียก managed GC พร้อม LOH compaction ครั้งเดียวเมื่อ UI ว่าง เพื่อคืนส่วน heap ที่ไม่ใช้แล้ว ไม่ใช้ timer หรือบีบ Working Set งานใหม่จะรอ cleanup ที่เริ่มแล้วแบบ async อาจมี GC pause สั้น RAM ของ WPF/.NET ที่ยังใช้อยู่ยังคงอยู่ จึงไม่รับประกันว่าจะเท่าก่อนงานทุกครั้ง ดู [ผลเทียบก่อน–หลัง](docs/idle-memory-fix-verification-2026-11-08.md)

### การลองคำขอ Google Drive ซ้ำและบันทึกวิเคราะห์

- คำขอที่ลองซ้ำได้จะลองรวมสูงสุด 6 ครั้งเมื่อ connection reset, HTTP timeout, HTTP 408/429/5xx หรือ 403 ที่มี reason `rateLimitExceeded`/`userRateLimitExceeded` โดย exponential backoff + jitter และ Retry-After ที่จำกัดไม่เกิน 60 วินาทีต่อครั้ง รวมถึงการต่ออายุ OAuth token
- การสร้าง encrypted object ใช้ Drive file ID ที่จองล่วงหน้า (ครั้งละ 100 ID) และใช้ ID เดิมเมื่อเริ่ม session ซ้ำ ป้องกันการสร้างไฟล์ซ้ำจากผลตอบรับที่สูญหาย การส่งข้อมูลยัง probe session ก่อนส่งซ้ำ และตรวจ uploadId/ขนาดก่อนยืนยัน เมื่อ session หมดอายุจะ reconcile กับวัตถุเดิมและตรวจ hash ก่อนยอมรับผลที่ไม่แน่นอน
- ไม่ retry การสร้างโฟลเดอร์แบบสุ่มเสี่ยงสร้างซ้ำ ไม่ retry ข้อผิดพลาดสิทธิ์/พื้นที่เต็มแบบไม่จำกัด ไม่ commit snapshot หากยังมีวัตถุที่ยืนยันไม่ได้ การยกเลิกจากผู้ใช้ไม่ถูก retry
- Log อยู่ที่ `%LOCALAPPDATA%\PCAutobackup\logs\google-<PID>.jsonl` หมุนไฟล์เมื่อเกิน 4 MiB และเก็บ `.previous` อีกหนึ่งไฟล์ต่อ process บันทึก UTC, operation, request ID, attempt, HTTP status, delay, exception type/HResult/HttpRequestError/socket error และผล retry ไม่บันทึกข้อความ exception ดิบ, URL, headers, request/response body, token, key หรือชื่อไฟล์
- ข้อความล้มเหลวเก่าที่เก็บเพียง `An error occurred while sending the request.` ไม่สามารถย้อนระบุสาเหตุเครือข่ายชั้นในได้ รุ่นใหม่ช่วยแยกสาเหตุเมื่อเกิดซ้ำ แต่ไม่รับประกันว่าการเชื่อมต่อที่ขาดนานจะสำเร็จ การอ่าน payload แบบ streaming ที่ขาดกลางทางยังอาจยุติรอบโดยเก็บ snapshot เดิมไว้

### รอการยืนยันหลังอัปโหลด

หลัง Drive ตอบรับข้อมูล แอปตรวจชื่อวัตถุ ขนาด และ uploadId หากผลค้นหายังว่างหรือยังเป็นเวอร์ชันเก่า จะอ่าน metadata ด้วย file ID เดิมและรอค้นหาซ้ำสูงสุด 8 ครั้ง (backoff รวมประมาณ 1.5 นาที ไม่รวมเวลาคำขอ) โดยไม่สร้าง session ใหม่หรือส่ง payload ซ้ำในขั้นตอนยืนยัน ต้องพบชื่อเดียวและเวอร์ชันที่ถูกต้องก่อนยอมรับ หากพบชื่อซ้ำ/วัตถุนอกคลังจะหยุดอย่างปลอดภัย หากรอครบแล้วยังยืนยันไม่ได้จะไม่ commit snapshot และคงชุดสำรองเดิมไว้

Log `upload-confirm` แยก `search-not-visible`, `search-version-pending`, `id-confirmed`, `id-not-visible`, `identity-conflict`, `confirmed-after-delay` และ `confirmation-exhausted` เพื่อแยกผลค้นหาล่าช้าออกจากวัตถุที่ยังอ่านด้วย ID ไม่ได้ โดยไม่บันทึกชื่อไฟล์หรือ token

### การตรวจ metadata และ MIME ของวัตถุเข้ารหัส

วัตถุเข้ารหัสใน Drive อาจมี MIME ของไฟล์ไบนารีชนิดอื่น เช่น `image/jp2` แอปใช้ parent, `pcabRole=object-v1`, ชื่อวัตถุ canonical, ขนาด/uploadId และการตรวจ AEAD/HMAC เป็นหลักฐานความถูกต้อง ไม่จำกัดการค้นหาไว้ที่ `application/octet-stream` อีกต่อไป จึงค้นพบและใช้ chunk เก่าที่มี MIME ต่างได้ โดยไม่สร้างสำเนาใหม่ ไฟล์ Google Workspace, folder และ shortcut ที่ติด marker เป็น object จะถูกปฏิเสธอย่างปลอดภัย

Log `MetadataChecks` ระบุผลของ `id`, `name`, `parents`, `pcabRole`, `mimeType`, `size`, `uploadId` เป็น match/mismatch/unsupported/version-pending และยอมรับ MIME ไบนารีต่างเป็น accepted-binary ไม่บันทึกค่าชื่อไฟล์ parent ID หรือ token หาก identity ขัดแย้ง ข้อความ error จะมีชื่อช่องที่ไม่ตรง MIME category ใน log จำกัดเป็น octet-stream, image/jp2, other-binary หรือ google-workspace-or-missing

### ชื่อ chunk ซ้ำใน Google Drive

หากพบหลาย file ID ที่ใช้ชื่อ chunk เดียวกัน แอปอ่านแต่ละสำเนาแบบจำกัดขนาด ตรวจ AES-GCM และ HMAC ให้ตรง content address เดียวกันก่อนเลือกสำเนาอ่านอย่างแน่นอน รองรับ ciphertext ต่างกันจาก nonce ที่สุ่มใหม่ โดยไม่อัปโหลด chunk เพิ่ม ไม่แก้ไขหรือลบสำเนาเก่า หากสำเนาใดเสียหาย ผิดกุญแจ ผิดชื่อ/parent/marker หรือเป็น Google Workspace จะหยุดและเก็บทุกสำเนาไว้ ชื่อ owner หรือ manifest ซ้ำยังคงหยุดอย่างปลอดภัย

รายการคลังแสดง chunk หนึ่งรายการต่อชื่อ แต่รวมขนาดทุกสำเนาในการคำนวณ quota การเขียนทับและลบชื่อที่ซ้ำถูกปฏิเสธ รวมถึงช่วง cleanup ซึ่งจะรายงานคำเตือนหาก snapshot commit แล้ว การแก้นี้ไม่ใช่การลบข้อมูลซ้ำย้อนหลัง Log `duplicate-object` ระบุจำนวนสำเนาและผล เช่น `authenticated-equivalent-chunks`, `chunk-authentication-failed`, `chunk-identity-mismatch`, `mutation-refused` โดยไม่บันทึกชื่อไฟล์หรือเนื้อหา

### ลดคำขอ Google Drive สำหรับไฟล์เล็ก

chunk ใหม่ที่มีข้อมูลก่อนเข้ารหัสไม่เกิน 256 KiB ใช้ multipart เพื่อส่ง metadata และข้อมูลเข้ารหัสในคำขอเดียว รวมการค้นหาชื่อก่อนสร้างและการยืนยันหลังส่งแล้ว ปกติใช้ 3 คำขอต่อ chunk จากเดิม 5 คำขอ ไม่นับการจอง ID เป็นชุดและการลองซ้ำ การลองส่งซ้ำใช้ file ID เดิม แล้วตรวจชื่อ ขนาด ID และ uploadId ก่อนบันทึก snapshot

เมื่อมี chunk จาก snapshot เดิมอย่างน้อย 1,024 รายการ แอปอ่านรายการ chunk ที่มีอยู่บน Drive แบบแบ่งหน้าเพื่อใช้แทนการค้นหาทีละชื่อ และตรวจรายการที่นำกลับมาใช้อีกครั้งก่อนบันทึก snapshot หากผลไม่ชัดเจนหรือชื่อซ้ำ จะกลับไปค้นหาชื่อและตรวจสำเนาตามปกติ การกู้คืนใช้รูปแบบ chunk และ snapshot เดิม
